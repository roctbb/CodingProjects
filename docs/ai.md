# Настройка ИИ

Администратору доступен раздел **Настройки** в выпадающем меню профиля, вкладка **ИИ**: `/insider/settings/ai`. В нём можно выбрать общий провайдер, модели и время ожидания, задать эндпоинты, ключи и HTTP(S)/SOCKS5-прокси обоих подключений, а также переопределить провайдер, модель и таймаут для каждой операции. На соседней вкладке находятся отдельные настройки Telegram.

Раздел доступен только существующей глобальной роли `admin`; учителя и ученики не могут читать, изменять или сбрасывать эти настройки. Перед использованием примените миграцию `2026_10_14_130000_create_ai_settings_table.php`.

Сохранённые значения имеют приоритет над `.env`. Они хранятся в таблице `ai_settings` в зашифрованном виде с использованием `APP_KEY`. Для чтения настроек после переноса приложения нужен тот же ключ шифрования. Ключи API и адреса прокси не возвращаются в HTML и не сохраняются в сессии при ошибке валидации. В форме для них доступны действия «оставить», «заменить», «удалить / без прокси» и «использовать серверную настройку».

Изменения из интерфейса применяются со следующей операции, в том числе в уже запущенных воркерах очереди. Общая кнопка восстановления удаляет переопределения из базы и возвращает конфигурацию сервера. Таймаут ограничен 180 секундами, чтобы запрос завершался до лимита фоновой задачи.

Все операции проходят по одному пути:

```text
Контроллер / генератор → ChatGptService → ApiClient → gateway / openai
                              ↓              ↑
                         ImagesClient ───────┘
                              ↑
                         AiSettings ← база данных
                              ↑
                         config/ai.php ← .env
```

Контроллеры и генераторы задают команду, сообщения и параметры картинки. `AiSettings` объединяет серверную конфигурацию и переопределения из базы при каждой операции. `ChatGptService` выбирает провайдера, модель и таймаут из этого снимка и извлекает текст или изображение. Для картинок можно выбрать Responses или Images API; `ImagesClient` преобразует сообщение в prompt и файлы референсов. Все внешние генерации проходят через `ApiClient`: HTTP, авторизация, прокси, формат шлюза и нормализация ошибок общие. В коде приложения нет прямых чтений `.env`.

## Собственный шлюз

```dotenv
AI_PROVIDER=gateway
GPT_KEY=your-gateway-key
GPT_GATEWAY=https://your-gateway.example/v1/responses
GPT_PROXY=
```

Это режим по умолчанию. Существующие `GPT_KEY`, `GPT_GATEWAY` и `GPT_*_MODEL` продолжают работать. Шлюз получает `{token, model, input}`; дополнительные параметры Responses (`tools`, `tool_choice`) передаются в `params`. Ожидаемый ответ: `{result: {output: [...]}}`. Ключ OpenAI шлюзу не передаётся.

## Напрямую в OpenAI

```dotenv
AI_PROVIDER=openai
OPENAI_API_KEY=your-openai-key
OPENAI_RESPONSES_URL=https://api.openai.com/v1/responses
OPENAI_PROXY=
```

Эндпоинт Responses — полный URL, включая `/v1/responses`, а не базовый адрес `/v1`. Ключ передаётся в `Authorization: Bearer …`; тело содержит `model`, `input` и, для картинок через Responses, `tools` и `tool_choice`. Поддерживается также другой эндпоинт, совместимый с Responses API и Bearer-авторизацией. Chat Completions сюда не подходит. Для Images задаётся отдельный адрес и формат, описанные ниже.

Прокси задаётся отдельно для каждого подключения, например `socks5h://user:password@proxy.example:1080` или `http://proxy.example:8080`. Специальные символы логина и пароля нужно URL-кодировать. Пустое значение означает прямое соединение, без системного HTTP-прокси. Прокси также применяется при скачивании картинки, если шлюз возвращает URL вместо base64; API-ключ при скачивании не передаётся.

По умолчанию картинки, как и текст, используют Responses API (`OPENAI_IMAGE_API=responses`). В этом режиме `GPT_IMAGE_MODEL`, `GPT_ACHIEVEMENT_IMAGE_MODEL`, `GPT_POSTER_MODEL` и `GPT_ROOM_CHARACTER_MODEL` задают **основную модель Responses**, которая вызывает инструмент `image_generation`; это не имя модели семейства `gpt-image-*`. У выбранной модели и API-проекта должен быть доступ к этому инструменту. Формат запроса описан в [документации OpenAI](https://developers.openai.com/api/docs/guides/tools-image-generation).

## Images API и NeuroAPI

Совместимость с Responses не означает поддержку всех hosted tools OpenAI. В частности, для NeuroAPI используется документированный [Images API](https://neuroapi.host/docs/images). В настройках администратора выберите основное подключение **OpenAI / совместимый API**, формат изображений **Images**, адрес `https://neuroapi.host/v1/images` и модель изображений `gpt-image-2`. Проверьте отдельные модели всех операций с изображениями: они имеют приоритет над общей моделью. Заполнение карточки подключения само по себе не выбирает его основным.

Эквивалентная серверная конфигурация:

```dotenv
AI_PROVIDER=openai
OPENAI_API_KEY=your-neuroapi-key
OPENAI_RESPONSES_URL=https://neuroapi.host/v1/responses
OPENAI_IMAGE_API=images
OPENAI_IMAGES_URL=https://neuroapi.host/v1/images
GPT_IMAGE_MODEL=gpt-image-2
GPT_ACHIEVEMENT_IMAGE_MODEL=gpt-image-2
GPT_POSTER_MODEL=gpt-image-2
GPT_ROOM_CHARACTER_MODEL=gpt-image-2
```

Для прямого OpenAI тот же формат работает с `OPENAI_IMAGES_URL=https://api.openai.com/v1/images` и его ключом. Адрес Images задаётся явно, не выводится из адреса Responses и не переключается при ошибке. Ключ и прокси берутся из того же подключения. Старые настройки без новых полей сохраняют прежний режим Responses; миграция базы не требуется.

- Без референсов: один JSON-запрос `POST /images/generations` с `model`, `prompt`, `n=1` и параметрами картинки.
- С референсами: один `multipart/form-data` запрос `POST /images/edits`. Файлы идут повторяющимися частями `image[]` в исходном порядке; текстовые части объединяются в prompt. Для персонажа первый файл — аватарка, второй — стандартный персонаж.
- Для персонажа передаются `size=1024x1536`, `quality=medium`, `background=transparent`, `output_format=png`. `tools` и `tool_choice` в Images не отправляются. `response_format` не задаётся: GPT Image возвращает base64 по умолчанию.
- Ответ `data[].b64_json` декодируется, временный `data[].url` сразу скачивается без API-ключа и сохраняется в нашем Storage. Проверяются реальные байты изображения.

Протокол редактирования, несколько референсов и параметры прозрачности описаны в [OpenAI Images Edit](https://developers.openai.com/api/reference/python/resources/images/methods/edit). NeuroAPI предупреждает, что доступность параметров зависит от модели и канала. Для `gpt-image-2` прозрачность в OpenAI имеет статус preview: результат всё равно проходит нашу проверку альфа-канала. Ошибка или непрозрачный результат приводят к возврату GC, а не к установке невалидного слоя.

`gpt-5.5` корректен как основная модель **Responses**, но не заменяет модель изображений в **Images**. Переключение формата не подменяет модель автоматически. Images предназначен для одной генерации/правки: история assistant/tool, удалённые ссылки и неподдерживаемые типы контента отклоняются до отправки. Наши генераторы передают локально подготовленные PNG data URLs; они преобразуются в multipart-файлы, без дополнительной загрузки через Files API.

## Выбор по командам

Пустой провайдер команды наследует `AI_PROVIDER`. Можно, например, оставить текст через шлюз, а кубки генерировать напрямую:

```dotenv
AI_PROVIDER=gateway
AI_ACHIEVEMENT_IMAGE_PROVIDER=openai
GPT_KEY=your-gateway-key
OPENAI_API_KEY=your-openai-key
```

| Команда | Провайдер | Модель | Таймаут |
| --- | --- | --- | --- |
| `text_improvement` — редактор текста | `AI_TEXT_IMPROVEMENT_PROVIDER` | `GPT_TEXT_IMPROVEMENT_MODEL` → `GPT_MODEL` | 60 с |
| `task_summary` — пересказ решений | `AI_TASK_SUMMARY_PROVIDER` | `GPT_TASK_SUMMARY_MODEL` → `GPT_MODEL` | 90 с |
| `achievement_variants` — три варианта достижения | `AI_ACHIEVEMENT_PROVIDER` | `GPT_ACHIEVEMENT_MODEL` (по умолчанию `gpt-5.5`) | 120 с |
| `achievement_image` — PNG кубка | `AI_ACHIEVEMENT_IMAGE_PROVIDER` | `GPT_ACHIEVEMENT_IMAGE_MODEL` (по умолчанию `gpt-5.5`) | 180 с |
| `course_poster` — постер программы | `AI_COURSE_POSTER_PROVIDER` | `GPT_POSTER_MODEL` → `GPT_IMAGE_MODEL` → `GPT_MODEL` | 180 с |
| `room_character` — персонаж по аватарке | `AI_ROOM_CHARACTER_PROVIDER` | `GPT_ROOM_CHARACTER_MODEL` → `GPT_IMAGE_MODEL` → `GPT_MODEL` | 180 с |

`GPT_MODEL` по умолчанию равен `gpt-5-mini`. Если явно оставить модель достижения пустой, применяется соответствующая общая модель: `GPT_MODEL` для текста, `GPT_IMAGE_MODEL` / `GPT_MODEL` для картинки.

Новая операция добавляется записью в `ai.commands`, названием в `AiSettings::COMMANDS` для формы администратора и вызовом `generate($messages, ['command' => '...'])` или `generateImage(...)`. Провайдер, ключи и URL не передаются из пользовательских форм.

## Персонаж комнаты по аватарке

Владелец профиля может создать или перегенерировать персонажа за **100 GC** в настройках комнаты. Для этого нужна загруженная аватарка PNG/JPEG/WebP до 10 МБ и до 32 мегапикселей. Перед отправкой создаётся PNG-копия размером не более 1024 пикселей по длинной стороне; исходная аватарка не изменяется. Для полученного от ИИ PNG сохраняется отдельное ограничение в 16 мегапикселей. Плата списывается вместе с созданием операции под блокировкой пользователя; идентификатор запроса защищает от повторного списания. Одновременно у пользователя выполняется только одна генерация.

`room_character` отправляет один запрос с двумя референсами (снимок аватарки и стандартный персонаж как образец стиля). В режиме Responses это два `input_image` и инструмент `image_generation`; шлюз должен передавать массив `input[].content` с base64-изображениями без изменения. В режиме Images это два файла `image[]` в `/images/edits`. Команда использует общие ключи, эндпоинты и прокси, а её провайдер, модель и таймаут доступны в настройках администратора. Удалённых платных запросов в автотестах нет: оба формата и шлюз проверяются подменой HTTP.

Готовые изображения записываются через стандартный диск Storage в `room-characters/user-<id>-<uuid>.png` (по умолчанию `storage/app/room-characters`) и отдаются через `/media`. `room_character_generations.result_path` хранит путь, а `users.room_character_generation_id` — активный результат. Статические файлы в `public/images/avatar-layers/room-system/characters` остаются шаблонами и запасным вариантом. PNG должен содержать видимый персонаж и прозрачный фон; его пропорции и положение ног нормализуются по шаблону. Старый результат удаляется только после успешной установки нового.

В Docker каталог `storage/app` находится в именованном томе `storage_app` (в рабочем Compose-проекте — `codingprojects_storage_app`), общем для `php`, `queue` и `scheduler`. Файлы хранятся вне слоя контейнера и сохраняются при сборке образов и пересоздании сервисов. Приватные снимки аналогично вынесены в отдельный том `storage_private`. При обновлении нельзя удалять эти тома (`docker compose down -v`); резервное копирование должно включать том с изображениями и базу данных со ссылками на них.

Временные снимки аватарок лежат на отдельном диске `room_character_sources`, в `storage/app-private/room-character-sources`, вне корня публичного `/media`. Они удаляются после завершения операции. При ошибке или отказе провайдера, сбое сохранения, недоступной очереди и таймауте возвращаются 100 GC, предыдущий персонаж сохраняется. Задание выполняется без повторного обращения к ИИ (`tries=1`, timeout 240 с). Запоздавший ответ после возврата не устанавливается.

Для готовых персонажей, кубков и постеров явно задаётся публичная видимость файла и каталога (на локальном диске — `0644` и `0755`). Это необходимо, когда очередь создаёт файл от `root`, а веб-процесс читает его от `www-data`. Ранее каталог мог создаваться с `0700`: генерация отмечалась успешной, но `/media` возвращал 404 и профиль показывал стандартного персонажа.

При развёртывании исправления существующие файлы нужно восстановить без повторной генерации:

```bash
docker compose exec -T --user root php php artisan media:repair-generated-permissions --dry-run
docker compose exec -T --user root php php artisan media:repair-generated-permissions
```

Команда меняет только права на каталоги `room-characters`, `achievement-trophies`, `course-posters` и лежащие непосредственно в них изображения; содержимое файлов, БД и монеты не меняются. Исходные аватарки и приватные временные снимки не затрагиваются. После выполнения проверить URL готового PNG и профиль через веб-процесс. Для нелокального диска команда завершится с ошибкой: там доступ управляется отдельно.

Для выпуска нужны миграция `2026_10_14_140000_create_room_character_generations_table.php`, сборка фронтенда и перезапуск воркеров. На сервере нужен PHP GD с PNG/JPEG/WebP. В Docker добавлен общий том `storage_private` для PHP, очереди и планировщика; после обновления нужно пересобрать и пересоздать эти контейнеры. На нескольких серверах оба каталога Storage должны быть общими для веб-приложения, воркеров и планировщика; готовые PNG и база должны попадать в резервные копии.

Планировщик каждую минуту выполняет `room-characters:recover`: возвращает плату за задания, ожидающие более 30 минут или выполняющиеся более 10 минут, и дочищает временные снимки. Ежедневный запуск с `--prune` удаляет файлы старше суток, оставшиеся без действующей ссылки после аварий или удаления пользователя. Планировщик необходим для возврата монет после аварийного завершения воркера.

Исправление опечаток и стиля в редакторе, а также `php artisan course:fix-typos` используют один `TextImprover` и команду `text_improvement`. Отдельного клиента Яндекса нет. Старый URL `/insider/yandexgpt/improve-text` сохранён как совместимый адрес того же обработчика.

## Применение настроек и диагностика

При изменении настроек через интерфейс обновлять кеш или перезапускать воркеры не нужно. После изменения именно `.env` обновите кеш конфигурации и перезапустите долгоживущие воркеры. Переопределения из базы сохраняют приоритет. Для обычного Laravel-развёртывания:

```bash
php artisan config:cache
php artisan queue:restart
```

В Docker Compose `.env` передаётся и веб-приложению, и очереди через `env_file`. Чтобы контейнеры получили новые значения окружения:

```bash
docker compose up -d --force-recreate php queue scheduler
```

Ошибки настройки останавливают запрос до отправки. Клиент не делает скрытых повторов и не переключается на другого провайдера при ошибке: это могло бы повторно оплатить генерацию. Повторы фоновых задач по-прежнему управляются очередью. Обычный успешный сценарий достижения состоит из одного запроса на три текста и одного запроса на PNG.

При ошибке HTTP в лог попадают провайдер, команда, модель, формат API, статус HTTP, request ID и короткие структурированные `error.code`, `error.type`, `error.param`, если провайдер их вернул. Из сообщения NeuroAPI может извлекаться только request ID. Ключи, свободный текст ошибки, тела запросов/ответов и base64 изображений не логируются. Неуспешный или незавершённый ответ не используется как готовый результат. По одному HTTP 400 без error.code нельзя отличить несовместимость запроса от нехватки квоты или другого отказа.

Проверки без обращения к внешнему API:

```bash
php artisan test --filter='ChatGptService|ImagesApiTransport|RoomCharacterGeneration|AchievementGeneration|AchievementTrophyGenerator|AiConfiguration|AiSettings|TextImprovement'
```
